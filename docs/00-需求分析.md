# NipaServer 需求分析（聊天记录整理）

> 整理自 Iroha 与 irigaS 的讨论（2026-07-24），以及 2026-07-12 的补充记录。

## 一、讨论的起点：NipaPlay 要不要做服务器版

讨论从「NipaPlay 的服务器形态怎么做」开始，出现过三条路线：

1. **NipaPlay 直接编译出 WebUI / 无头版本**（irigaS 最初的想法）
   - 在服务器上无头部署 NipaPlay，通过 WebUI 配置扫描和下载；
   - WebUI 是客户端的"镜像/遥控"，操作交给客户端执行；
   - 优点：功能天然同步，不用维护两套代码；
   - 顾虑（Iroha）：播放器和服务器合在一起不优雅，NipaPlay 里已经有三个 ffmpeg，再加服务器功能会更复杂；服务器场景下播放器的绝大部分功能用不到。

2. **完全独立重写一个服务器**（Iroha 最初的想法）
   - 服务器本质上是个 Jellyfin 类似物，核心是"海报墙 + 控制台"，与播放器的显示逻辑完全不同；
   - 顾虑（irigaS）：单独写造轮子太多，新功能要维护两次，后期容易弃坑。

3. **最终共识：用 Rust 单独写一个"服务端核心"，两边复用** ✅
   - 单开一个仓库，用 Rust 写全新的刮削器/媒体库核心；
   - 先以独立服务器（WebUI）形态跑通；
   - 成熟后整合进 NipaPlay 客户端，替换现有扫描器——Rust 代码两边通用；
   - NipaPlay 客户端也能唤起 WebUI，个人电脑、甚至旧手机都能当媒体服务器（"不要的旧手机秒变媒体库"）。

## 二、为什么要重写：现有方案的问题

### NipaPlay 现有本地媒体库的局限
- 扫描方式太局限：**只能处理动漫**，太依赖弹弹play 的 hash 识别，"不是一个合格的媒体库"。

### Jellyfin/Emby 的问题
- 扫描/刮削非常原始：**关键词匹配不靠谱**，文件夹名字会变成干扰；
- "Jellyfin 最近变得好难用"（2026-07-12）；
- 结论：**不能再走 Jellyfin/Emby 的老路，都 LLM 时代了**。

## 三、核心创新点：围绕 Agent Loop 的媒体服务器

这是整个项目最核心的设计决策：

- **新的媒体服务器围绕 agent loop 展开**，包括文件结构管理；
- 刮削流程分两级：
  1. **第一批：弹弹play hash 匹配**（文件前 16MB hash），最快最准，但只覆盖动漫；
  2. **第二步骤：AI 刮削**——hash 没扫出来的，交给 agent 处理；
- AI 的信息来源：
  - 文件名、文件夹结构；
  - **视频元数据**（大部分字幕组的视频，文件元数据里会写明内容）；
  - **字幕内容**——AI 通过阅读字幕推断这是什么动画/剧集；
- **老式刮削器全部封装成 tools**，由 AI 自己去查：查到后写进数据库，拉取图片和海报；
- Agent runtime 不自己实现："我们怎么可能自己去实现完整的 agent"——**直接把 codex（Rust 写的）核心代码搬过来剪枝**（"精简重写 jellyfin + 剪枝 codex runtime"）；
- 模型档位：不需要深度思考（xhigh 太慢），**flash 级模型完全够用**——"不要求脑子，只需要你看到文件名，你去查，查到写进数据库"。

## 四、功能范围

### 媒体库 / 刮削
- 扫描服务器文件 → 媒体库 → 在线播放（播放是附带的，服务器要提供转码）；
- 元数据源：**Bangumi、豆瓣、TMDB**——"只要有 Jellyfin 插件的都可以，照着抄就行"；
- 弹弹play hash 匹配保留为第一级；
- 自建 hash 服务器扩展覆盖范围被否决（太费钱、用户不够）。

### 下载 / 订阅
- 内置种子下载（把目前 NipaPlay 的种子下载器搬过去/复用）；
- **订阅机制**（追番自动下载）；
- 保留"下载完自动扫描入库"的机制（现有 NipaPlay 已有，体验好于 qbit + Jellyfin）。

### 远程挂载 / 整合（irigaS 提出，Iroha 觉得不优雅，未定论）
- WebUI 直接连接 SMB / WebDAV / Jellyfin / Emby（类似 openlist 的整合思路）。

### 客户端关系
- 本地 NipaPlay 客户端直接连接远程服务器访问；
- Web 端主要做管理 + 基础播放（海报墙 + 控制台）。

## 五、产品形态与发布

- 单开一个新仓库开发；
- Release 提供两种形态：
  1. **带 UI 版本**（WebUI）；
  2. **无头模式的纯服务器扫描器版本**（纯 Rust）；
- 开发完成后接入 NipaPlay：
  - 替换现有扫描器；
  - 移除原种子下载器，复用新代码；
  - WebUI 在 NipaPlay 设置里单开一页，客户端内也能用。

## 六、商业模式

- **社区版**：暴露 API 接口，用户自带 API key（也看看有没有免费 API）；不支持订阅；
- **苹果商店版**（Mac App Store 需要上架）：不允许自定义 API key，只能走**订阅**，API 由订阅提供；
- 注意弹弹play 协议：盈利点不能是弹幕本身；
- iPhone 上跑 server 不太现实（未定论）。

## 七、关键决策一览

| 决策 | 结论 |
|---|---|
| 架构路线 | Rust 独立仓库写服务端核心，先 WebUI 独立跑，后整合进 NipaPlay |
| 刮削策略 | 弹弹play hash 第一级 + AI agent 第二级 |
| Agent runtime | 剪枝 codex（Rust）核心代码，不自己造 agent 轮子 |
| 刮削器定位 | 传统刮削器（TMDB/Bangumi/豆瓣）封装成 tools 供 AI 调用 |
| 模型 | flash 级即可，不用深度思考 |
| 模型接入 | 社区版暴露 API key 配置；商店版订阅制 |
| 下载 | 内置 BT 下载 + 订阅追番 + 自动入库 |
| 发布形态 | WebUI 版 + 无头纯扫描器版 |
